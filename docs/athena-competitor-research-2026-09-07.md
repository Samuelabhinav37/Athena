# Athena: comparable identity-governance approaches

Research date: 2026-09-07. Scope: public first-party documentation and product pages; no vendor tenant testing, purchasing assessment, or independent security audit. ConductorOne documentation now redirects to the C1 domain; this report uses C1 / ConductorOne together for clarity.

Athena's project instructions define an evidence-first governance system: collectors observe access, OPA decides policy outcomes, ML recommends, the LLM explains, and a human approves destructive actions before a separately authorized executor acts and verifies. The following lessons are recommendations, not claims that Athena already implements them. See [Athena project instructions](../AGENTS.md).

## Four-vendor comparison

| System | Documented approach | Operational constraint / evidence boundary | Practical lesson for Athena |
| --- | --- | --- | --- |
| Microsoft Entra ID Governance | Entitlement packages, delegated approvals, separation-of-duties checks, recurring reviews, lifecycle workflows, and PIM for privileged access. [Overview](https://learn.microsoft.com/en-us/entra/id-governance/identity-governance-overview) | Provisioning logs expose steps and errors, can stream to Azure Monitor, and document retries for transient failures. These are configured capabilities, not proof every downstream permission disappears immediately. [Operations](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/howto-analyze-provisioning-logs) | Make lifecycle state, approval ownership, failure reason, and log retention visible in the same case. |
| SailPoint Identity Security Cloud | Lifecycle states and requested access drive provisioning; certifications prevent self-certification and route removals through automatic or manual remediation. [Provisioning](https://documentation.sailpoint.com/saas/help/provisioning/index.html), [Certifications](https://documentation.sailpoint.com/saas/help/certs/understanding_certifications.html) | Direct connections can provision automatically; flat-file sources need human tasks. Access assigned by automated role criteria cannot simply be revoked like a requested role. The originating access model matters. [Certifications](https://documentation.sailpoint.com/saas/help/certs/understanding_certifications.html) | Explain where access originates and whether removal requires changing a parent role, policy, or manual source. |
| C1 / ConductorOne, with Baton connectors | Separate request, review, and revoke policies support distinct approvers and escalation; configured maximum request duration triggers expiry revocation. [Salesforce](https://www.c1.ai/docs/baton/salesforce), [Health](https://www.c1.ai/docs/baton/health-checks) | Publish capability per operation, and make waiting, escalation, retry, and manual work first-class states. |
| Veza | Its product describes an effective-permissions graph; Access AuthZ describes provisioning/deprovisioning through native, SCIM, and OAA Write integrations. [Product](https://veza.com/product/), [Access AuthZ](https://veza.com/product/access-authz/) | May 2026 updates describe per-attempt remediation events, exportable review reports, and specific connector permission improvements. These are vendor descriptions, not independent proof of coverage or uptime. [Updates](https://veza.com/blog/veza-product-updates-may-2026/) | Preserve permission lineage and log every attempted remediation, including failures; improve each connector's semantic coverage incrementally. |

## What they document about fighting access risk and maintaining the workflow

- **Reduce standing privilege:** Entra documents PIM just-in-time access with MFA and Conditional Access alongside governance. This is a privileged-access control integrated with a broader identity system; it should not be equated with Athena's observational policy evaluation. [Entra overview](https://learn.microsoft.com/en-us/entra/id-governance/identity-governance-overview)
- **Avoid approval bottlenecks:** C1 policies can require different approvers across steps, request justification, and escalate overdue tasks by reassigning, changing policy, cancelling, or skipping a step. Athena should favor reassignment or cancellation for sensitive work, preserving required human approval. [C1 policies](https://www.c1.ai/docs/product/admin/policies)
- **Give temporary access a real end:** C1 documents maximum request duration and automatic revocation at expiry. Athena should distinguish an expired approval from verified removal at the target; expiry alone is insufficient evidence. [C1 request configuration](https://www.c1.ai/docs/product/admin/access-requests)
- **Keep maintenance failures actionable:** Microsoft identifies authorization/configuration errors separately from transient target failures and provides downloadable provisioning logs. C1 documents up to five attempts for provisioning 503 errors, no retry for 401/403/404 configuration errors, and manual fallback. [Microsoft logs](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/howto-analyze-provisioning-logs), [Baton health](https://www.c1.ai/docs/baton/health-checks)
- **Acknowledge manual remediation:** SailPoint creates a source-owner task when direct writes are unavailable. A revoke decision must be signed off to apply. Athena can remain read-only and still offer valuable governance if ownership, due dates, evidence attachments, and independent verification are explicit. [SailPoint certifications](https://documentation.sailpoint.com/saas/help/certs/understanding_certifications.html)
- **Maintain connectors as software:** ConductorOne publishes shared connector workflows for linting, tests, optional regression verification, and account-provisioning tests. This is evidence of an available engineering mechanism, not proof that every connector passes a universal conformance suite. [Connector workflows](https://github.com/ConductorOne/github-workflows)
- **Improve operator usability continually:** Veza's May release includes previous-review comparison, per-reviewer progress, decision filters, and remediation reporting. Athena should measure time to decision and time to verified closure while reducing unnecessary reviewer navigation. [Veza May updates](https://veza.com/blog/veza-product-updates-may-2026/)

## Recommended work for Athena

These are engineering inferences from the comparison and Athena's stated design boundary, not a substitute for local code verification.

1. **Show what is known.** Each decision should include snapshot time, connector coverage, missing telemetry, source of the entitlement, and policy version. Unknown activity must be visibly distinct from observed inactivity.
2. **Close the case without pretending to remove access.** Use explicit states for human approval, manual or authorized execution, target verification, and failure. A ticket closure or successful API response is not by itself evidence that effective access vanished.
3. **Make connector coverage granular.** Document discover, normalize, calculate inherited access, request, grant, revoke, and verify independently. Never infer a write capability from a read integration. Do not broaden Athena's read-only tokens to copy a vendor feature.
4. **Make human work manageable.** Provide stable owner identities, complete pagination/search, assignment, reminders, reassignment, and due dates. Show a concise explanation with links to underlying evidence; keep the LLM advisory.
5. **Treat workers as recoverable state machines.** Design bounded retries, lease recovery, idempotency, timeout reasons, rate-limit handling, and a manual exception queue. Preserve every attempt as evidence.
6. **Measure the service you actually provide.** Track data freshness, collection completeness, oldest unresolved review, verification delay, failed attempts, and restoration drills. Set targets after measuring a pilot; no vendor SLA or numerical target is assumed here.

## Limits of this comparison

The sources document intended features, configuration, and selected implementation practices. They do not establish comparative breach rates, universal connector completeness, tenant isolation effectiveness, penetration-test results, incident response quality, or independently measured reliability. Pricing and license availability were not evaluated. A product logo or integration count does not establish permission-level coverage. Veza evidence here is predominantly product and release material and carries less implementation detail than the Microsoft, SailPoint, and C1 operational documentation. No shared claim that all four vendors independently read back every removal was substantiated; target verification is therefore an Athena recommendation rather than a universal vendor fact.

Documentation-only research: no application code, policies, credentials, live connectors, database, or access decisions were changed. Application test and security-gate status are outside this research subtask and must be reported by the main assessment.
