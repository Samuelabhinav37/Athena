01 / The evidence lifecycle

One record of truth. Separate responsibilities.

Select a stage to inspect its input, output, and implementation.

Stage 01 / Read-only collection

Observe access at its source.

Keycloak, GitHub, and Microsoft Azure collectors read approved provider scopes. Capability manifests describe what each connector can and cannot establish.

Input → output

Provider records → bounded identity and access snapshots.

Code reference
collectors/contracts.py

Connector credentials are read-only; collected records are evidence, not instructions.

System of record

PostgreSQL + tenant isolation

Tenant context accompanies requests and jobs. Tenant-aware constraints and forced row-level security protect separation. Historical evidence is append-only; current operational state can advance.

Continuous operation

Monitor, checkpoint, repeat

Monitoring uses schedule keys, database leases, heartbeats, and recorded steps. Replaying a completed schedule is a no-op. Failures and recovery attempts remain visible.

OPA / Rego

Authoritative policy evaluation. Canonical inputs, a versioned policy bundle, and recorded violations support reproducibility. An “allow” evaluation does not issue an upstream grant.

Analytics + explanations

Access-decay factors and fixed-seed peer anomalies inform review. Ollama or guarded Azure AI can explain bounded evidence; generated prose cannot drive policy or execution.

Neo4j

Optional, rebuildable projection of authorization evidence for bounded attack-path queries. Graph results are advisory; PostgreSQL remains authoritative.

03 / What is actually connected?

Coverage is explicit, including the gaps.

Based on the collectors’ capability manifests, which are more precise than broad README capability summaries.

Current collector snapshot contracts
SourceCollected evidenceImportant boundary
KeycloakRealm users, current roles, groups, and group paths.Partial lineage and nesting; no activity feed or deny-policy collection. This snapshot explicitly excludes service-account users.
GitHubOrganization members, teams, repositories, reported effective permissions; pagination and endpoint ETags.No parent-team resolution, Apps/bot inventory, activity logs, or full grant lineage. ETags are not a provider-wide incremental cursor.
Entra ID + Azure RBACUsers, groups, direct member IDs, role assignments, service principals, managed-identity type, owners, and credential metadata.No recursive group expansion, deny assignments, PIM eligibility, or activity logs. RBAC scope is preserved without fully expanding inheritance.

All three manifests declare retries unsupported inside the collector. Orchestration must handle retries. Missing activity evidence must not be presented as proof of inactivity.

Reviews and remediation

Review cases, immutable events, idempotent execution requests, and an injected-adapter worker contract exist. Production GitHub and Azure remediation adapters remain planned; read-only collectors cannot fulfill a revoke request.

Machine identities and attack paths

Dedicated services assess machine identity ownership, activity, credential age, and access posture. Source coverage varies: Azure declares machine discovery supported; the current Keycloak and GitHub snapshot manifests do not. Optional Neo4j queries derive from collected authorization facts.

Telemetry and protection agents

JSON, OTLP/JSON, RFC 5424 syslog, signed-webhook normalization, and deterministic export contracts exist. General telemetry normalization is not durable ingestion or delivery acknowledgement. Moat/Clutter protection-agent enrollment, signed policy, and event routes are a separate bounded domain.

Reporting and compliance

Evidence reports render as digest-verified JSON and Markdown. NIST mappings and an OSCAL-compatible Component Definition describe control support, not certification. PDF, Word, and OSCAL Assessment Results are not active evidence renderers.

Analyst interface and future workflow

The React dashboard includes a command center, investigations, identity evidence, connector coverage, review workspace, and system setup. A full access-request and approval product workflow remains roadmap work; an existing review mechanism is not proof of that complete workflow.
