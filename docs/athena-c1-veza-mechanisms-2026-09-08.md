# How C1/Baton and Veza implement the problems Athena faces

Researched 2026-09-08 against official technical documentation. This follows the feature comparison with mechanisms, boundaries, and a worked example. Documentation describes a contract or intended behavior; no vendor tenant was exercised and no claim of universal connector correctness or breach resistance is made. These are recommendations for Athena's design, not application changes.

## C1 / ConductorOne: normalize access, then orchestrate connector work

**1. A small connector contract produces a common access graph.** A resource is an account, group, repository, or role; an entitlement is assignable access on that resource; a grant connects a principal to an entitlement. The SDK walks resource types in stages: resource instances, entitlements, then grants. Stable external `RawId` values flow into sync records and domain correlation rather than relying on display names. Parent-resource IDs preserve hierarchy. This describes how different APIs become comparable, while connector authors still choose permission granularity. [C1 core concepts](https://www.c1.ai/docs/developer/concepts)

**2. Pagination is a state protocol.** Connector methods return one page plus a continuation token. The SDK repeatedly calls them until the token is empty. The guidance warns that an empty result page may still have a continuation token. For nested organizations/teams/members, `pagination.Bag` serializes a stack containing token, resource type, and resource ID; push/pop operations track traversal. This separates fetch progress from result count and prevents losing later pages merely because an intermediate page is empty. [Pagination patterns](https://www.c1.ai/docs/developer/pagination)

**3. Incremental collection is connector-specific.** The Azure DevOps connector documents an optional mode that reads audit logs to capture changes between full syncs; it requires Audit Log: Read permission. That is a concrete event source plus periodic baseline pattern, not a guarantee that every Baton connector supports deltas. A pagination cursor within a full scan is also not necessarily a durable change-feed cursor. [Azure DevOps connector](https://www.c1.ai/docs/baton/azure-devops/)

**4. Approval routing is an ordered rule engine.** C1 separates request, review, and revoke policy types. It evaluates rules from most specific to fallback, taking the first match. Review steps can require distinct approvers and justification; timed waits have explicit timeouts, and overdue tasks can be reassigned, cancelled, or routed through another policy. A denied review can create a separate revoke task. This supplies a mechanism for reducing waiting without treating a review decision as a completed target-system change. [Policies](https://www.c1.ai/docs/product/admin/policies)

**5. Execution carries the actual target identifiers.** `Revoke` receives a grant; `Grant` receives principal and entitlement. The guide recommends retaining a target assignment ID for precise removal and validating principal type. V2 grants return a list because one logical request can create multiple underlying grants. Already-existing/already-removed outcomes have explicit annotations for retry-safe behavior. Optional interfaces determine advertised capabilities. The example treats a known missing assignment as success; it does not establish that all effective access or active sessions disappeared. [Implementing provisioning](https://www.c1.ai/docs/developer/provisioning)

**6. Workers renew ownership of tasks.** In daemon mode, the connector polls via gRPC, heartbeats during work, and reports success/failure through `FinishTask`. Missing heartbeats may cause reassignment. Sync output is streamed in chunks. This gives a documented recovery mechanism for dead workers, but does not prove exactly-once downstream execution. A worker can fail after a target write and before reporting completion, so the idempotent target operation remains important. [C1 API integration](https://www.c1.ai/docs/developer/c1-api)

**7. Failures have a recovery path.** Baton health documentation distinguishes process liveness, client readiness, and connector validation. It describes up to five provisioning retries for 503 errors, with configuration errors such as 401/403/404 not retried and unresolved work falling back to manual follow-up. This general error classification must be interpreted with the target-specific idempotency contract: an assignment already absent is different from an invalid endpoint. [Connector health checks](https://www.c1.ai/docs/baton/health-checks)

## Veza: separate authorization modeling from account lifecycle writes

**1. The connector supplies semantic meaning.** OAA models local users/groups, federated identities, roles, and resource-scoped permissions. Connector authors map provider-native permissions such as Pull or Merge to canonical categories such as Data Read or Data Write. Roles collect permissions; users can receive roles or direct permission assignments. The documentation cautions that an application's object called a role may actually behave like a group. The normalized graph therefore depends on correct translation of source semantics, rather than the product discovering meaning from names alone. [Modeling users, permissions, and roles](https://developer.veza.com/oaa/guide/core-concepts/modeling-users-permissions-and-roles)

**2. Cross-system identity links are explicit.** Local-user `identities` values can match IdP unique IDs, email, and certain provider-specific attributes. Local-group identities can link to IdP groups, carrying the group's users into that access path. Unresolved identities produce warnings while the local user is still created. This lets the system preserve a discovered account without pretending its human owner is known. Email matching is supported, but the documentation is not a universal guarantee against ambiguous, recycled, or misconfigured identity values. [Cross-service connections](https://developer.veza.com/oaa/guide/core-concepts/cross-service-connections)

**3. Delta updates require an established baseline.** The first OAA push must be full. Later payloads set `incremental_change: true` and specify operations such as add, modify, delete, or resource-scope changes. The guide recommends full extraction when the source cannot reliably track changes. It also specifies payload constraints, including restrictions on combining operations. An OAA delete updates graph metadata; it should not be confused with deleting an account in the source application. This page does not promise transactional recovery or deduplication of arbitrarily replayed event streams. [Incremental updates](https://developer.veza.com/oaa/reference/incremental-updates)

**4. Graph ingestion has instance boundaries.** OAA registers a provider and one or more data sources; a source can represent a production instance separately from development. The connector publishes a structured metadata payload for the particular source. This identifies the integration instance instead of flattening every application with the same product name into one object. The API documentation recommends checking for existing provider/source objects before creating them. [OAA Push API](https://developer.veza.com/oaa/reference/api/oaa-push-api)

**5. The write path is configured independently.** OAA supplies graph visibility; external SCIM configuration supplies lifecycle endpoints and credentials. The two configurations must describe consistent users/groups. Lifecycle actions map to SCIM operations: deactivation sets `active=false`, while deletion removes the account. Built-in SCIM discovery covers users/groups; richer roles/resources can be modeled separately with OAA. The document also describes custom REST actions with responses captured in audit trails. It does not establish universal post-write read-back verification. [OAA with SCIM lifecycle management](https://developer.veza.com/oaa/guide/core-concepts/oaa-scim)

## Worked example: Alice moves out of Engineering

Assume Alice has production write access through an Engineering group and an additional direct repository assignment. This is an illustrative mapping onto the documented mechanisms, not a tested vendor workflow.

| Question | C1/Baton mechanism | Veza mechanism | Athena design implication |
| --- | --- | --- | --- |
| Is this still the same account after a rename? | Stable external resource IDs support correlation across syncs. | A local account carries explicit IdP mapping values. | Retain immutable source IDs and display identity-mapping uncertainty. |
| How is the group path represented? | A user-to-group-membership grant and a group-to-repository entitlement can be represented; inheritance needs the connector's appropriate expansion modeling. | A local/IdP group link and scoped role/permission mappings carry group-based access. | Preserve all contributing edges; do not flatten the explanation to one role label. |
| How does the system notice the move? | A connector may use a supported change feed between full scans; all collection pages still need traversal. | Full metadata extraction or explicit delta update changes the represented membership. | Know which sources are fresh, complete, and capable of reporting deletions. |
| Who approves removal? | An ordered policy assigns review; a denied review can create a revoke task. | These developer sources establish graph and write primitives, not every approval routing guarantee. | Keep approval independently recorded and bound to the intended target. |
| What changes downstream? | A grant-specific revoke uses its principal, entitlement, and target assignment ID. | A separately configured lifecycle path updates SCIM user/group state. | A metadata change alone cannot enact removal; read-only collectors remain read-only. |
| Is Alice's production access now gone? | Removal of the group grant does not logically prove the separate direct grant is gone. | Updating group membership does not logically remove an independently modeled direct permission. | Recompute remaining paths using fresh observations before declaring effective access removed. |

For the hierarchy row, parent/child containment alone should never be treated as access inheritance. The consulted core docs establish the graph vocabulary and hierarchy support; exact nested-grant expansion requires additional connector-specific evidence. Both systems still depend on source APIs, supported semantics, configured permissions, and complete collection.

## Specific adaptations worth considering for Athena

These are engineering recommendations rather than documented vendor guarantees:

1. **Adopt a connector conformance contract.** Test stable IDs, role scope, direct/group overlap, empty continuation pages, deletion observation, and incomplete scans. Attach coverage and last-success metadata to each snapshot.
2. **Keep facts distinct from interpretations.** Store the source-native privilege, normalized category, normalization version, and identity-link confidence. Missing activity and unknown ownership should stay unknown.
3. **Bind execution to reviewed evidence.** Record principal, tenant, resource, entitlement, source assignment ID, policy/snapshot version, and expiry. Revalidate before a separately authorized executor acts.
4. **Recover worker ownership safely.** A durable lease, heartbeat, attempt journal, and idempotency key make interrupted work diagnosable. A recovered worker must distinguish not-started, unknown outcome, and confirmed completion.
5. **Verify the actual closure condition.** Treat approval, dispatch, target API response, and fresh observation as separate evidence events. A removal is complete only relative to an explicit goal: one assignment removed, account disabled, or all production-write paths absent.

Only this research file was created. No live write, credential access, application change, or executable vendor trial was performed. Technical sources substantiate mechanisms and documented constraints; they do not establish deployed security, universal semantics, or service-level performance.
